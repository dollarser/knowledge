## 1. 把Agent纳入经营实验，先交代资源和人工责任

### 工具试用量与Skill实验，只能先保留为使用线索

主持人提Muse、GrokBot两工具，主观试用体感不错。一位来宾说Muse十亿token已用近五亿，具体计量口径和产品身份不清。来宾前一晚整理提示词、架构、类似Skill的框架，白天反复测试，认为加Skill后有改善；没有给出完整效果和系统验收结果。国内大厂两个月追平Muse是个人预测，非进度承诺。

### 把经营范围、预算、资源和授权交给Agent，人工仍处理线下与责任

杨总正在试把公司经营范围、资源、预算和授权提供给个人Agent，要求其定策略、执行、复盘后迭代；Agent主动提示某项进展需要本人出差和线下跟进，否则线上工作没有结果。人仍要决策、担责、关联客户资源，“办公室全部人能替代”仍是他的判断，没有完成裁员的证据。旁人输入多年炒股理念、阈值后让Agent提醒买卖是二手用法，未证收益，尚不构成全自动投资有效的证明。前述Muse、豆子/Dose/GrokBot近音产品身份待确认。

### 技能快速迭代的体验，不等于某职业已经消失

杨总称自己早期用Coze做公司产品，发豆包获得大几千访问，后来平台智能体下架，仍在Coze；这只是本人转述。又以熟悉Premiere、3D Max、剪映、做过二百多篇视频新闻的经验，判断AI会替代逐帧剪辑、遮罩等工作，甚至称今年八到十月岗位到尾声，属预测。另一人说百炼、千问、DeepSeek、火山等一两周就迭代，旧版要更新，是自己维护负担。曾积极推广豆包的摄影徐导也可能追不上技能变化，讨论价值在以实际结果检验能力，而非只会演示熟悉工具。另一参与者将自己首产品十几天、每天十八小时与第二产品两天相比，未说明项目等复杂度，也不能归成生产率倍数，次日见CTO的说法后来纠正为见CEO汇报，不当应聘事实。

## 2. 十万元基金系统：最后一成与场景容错

### 全 AI 敏捷开发的“尾部陷阱”：前 90% 只要几天，最后 10% 死磕一个月
资深企业数字化服务操盘手杨总，复盘了去年 6 月带领团队为一家金融机构交付“十万元基金管理系统”的切身经历：
- **AI 极速开发的高光时刻**：团队深度采用当时前沿的前端与全栈 AI 代码生成工具（如 v0.dev 等），仅用了短短几天时间，就极其惊艳地完成了系统约 85% 至 90% 的页面布局、路由框架、交互表单与基础业务逻辑；
- **最后 10% 吞噬整月工期**：然而，当项目进入真实的业务深水区时，最后的 10% 却让团队整整折腾了近一个月：
  - 金融场景中严苛的边缘状态处理（如多币种清算截断、特定权限下的不可逆审核流、并发修改冲突）；
  - 大模型在长流程中偶发的细微逻辑幻觉，使得生成代码在某些特定参数下频频产生隐蔽 Bug，导致团队陷入反复推倒重来与代码审查的漫长泥潭；
- **工程启示**：AI 可以在第一阶段大幅缩短原型开发周期，但绝不等于工程尾部交付成本为零。越是严肃场景，边缘边界与异常处理越需要资深人类工程师的强工程兜底。

### 幻觉治理的工程经济学：定义场景容错，拒绝空谈“百分百消除”
杨总结合基金管理系统的实战教训，提出了对大模型“幻觉问题”的工程化思考：
1. **盲目追求 100% 消除幻觉在经济上是不可行的**：
   大模型的底层基于概率分布采样，理论上无法通过简单的 Prompt 调优做到数学级绝对精确。如果一个团队为了追求 100% 零幻觉而无限增加校验链条与模型轮询，由此引发的延迟与算力成本将彻底摧毁商业可行性；
2. **按场景严格划分容错等级（Fault Tolerance Hierarchy）**：
   真正的企业级架构应当根据业务场景的破坏性后果，定义明确的容错边界：
   - **零容错区（硬编码熔断）**：涉及基金申购赎回计算、资金划拨、交易权限审计等核心环节，绝不允许大模型自由发挥，必须交由确定性的后端业务规则引擎与数学公式执行；
   - **高容错区（大模型主导）**：对于研报核心观点提炼、同业竞品舆情摘要、多维市场信息初筛等辅助展示环节，允许在一定置信度区间内由模型自主生成，并明确提示业务人员做终审把关。

### 落地自查与实操演练建议：AI 敏捷开发尾部风控与幻觉分级 Checklist
1. **工期预估“二八黄金法则”**：
   - 在使用全 AI 编程工具承接外包或自研项目时，切忌按“首版 Demo 耗时”线性推导交付时间；必须将总工期的 50%–60% 预留给最后的联调测试、数据边界与异常状态排障；
2. **核心业务“三层容错矩阵”落地**：
   - 在系统架构设计之初，梳理业务字段清单：标注哪些属于“强确定性写操作（必须规则校验）”，哪些属于“宽容性只读展示（允许模型润色）”，杜绝将核心资金链条交给大模型裸跑。

## 3. 博思AI：从多模型辩论需求起步

### 杨总博思AI从多模型辩论的单点需求开始

随后受邀分享的嘉宾被介绍为杨思毅/思怡，前蚂蚁数据中台人员、博思AI与思维编译器相关创始CTO。姓名近音与“数据小天瑞士认证”等称谓不清，无外部履历认证；开源MetaStor及第一代/五代架构口述，其官方项目史仍待核实。他自述十几年写代码，三月才开始用AI，一个原本人工两小时的JSON银行卡消费报文解析任务，AI不到五分钟完成结构化，带来震撼；

博思AI需求来自身边人每次要分别问千问、豆包、DeepSeek，得到不同回答。于是做聚合平台让多个模型辩论，保留短期与长期记忆、不同角度结论，给用户共识和差异自行判断。“最中性”是产品目标，不是多个模型共识就可靠的证明。开始只做Spring Boot工程与模型适配SPI，不先上动态扩容、复杂CI/CD、全套架构；新增需求出现后再改造。初版同样出现一两百行一个方法，不是用了AI就自动高质量。

### 从参数膨胀发现领域模型，把重构约束写进Prompt

嘉宾举前后端传参从两三个增加到五六七八个，可抽成通用model/DTO。AI不会主动替你选择业务边界，要明确它哪些模块可复用、哪些必须分开。他习惯每步多想一点：对象会不会成为大对象、并发下选何种map、回收和内存怎么处理，再把这些约束写成Prompt，要求一边实现需求一边重构。其中GVM、corporate hashmap等为近音未确认的技术词；重要的是指出资源/线程安全约束，而不是机械套某容器。

多Agent按模块做抽象与整合，策略、工厂、观察者等只是可选模式，不是必须每种都加。他自述以前一次大升级连测试、灰度上线约一个月，如今一晚约两小时，14天时间线上有七百多或九百用例全绿，数字本身不定；未独立核仓库和测试范围，不能当普遍倍数或生产正确性认证。LLM适配模块可从博思AI单独抽为可部署通用模块，以异构数据源中间件经验设计，不表示自己训练基础模型，他明确模型调参没做。

嘉宾将可复用路径分需求理解、需求边界、技术架构。架构清单包括Spring Boot应用、结构化/非结构化/元数据存哪、一级二级缓存怎么取存、高可用、压测、多实例部署。产品经理可更懂需求，不必先掌握每种存储的全部底层调参，但要知道组件解决什么问题；Redis、OSS、MySQL以及向量库被举作用。Milvus又被口述或识别为Mistral，原词不稳定，不能把向量数据库等同完整知识图谱数据库或据此编API教程。文件图片视频、关系数据、语义检索是不同用途，应依业务确认。

嘉宾说在自己的有向无环图、longchings/long graph等近音框架中重写了部分逻辑，但没有仓库或实现可核，不能直接认证LangChain/LangGraph版本。Harness、loop、context、prompt被看作编排、workflow或状态流转的框架，需与业务结合，而非知道名称就能照搬。并行计算参考Hadoop和Storm的批流思路，多worker进程、容器CPU内存和core资源；线程不是无限起，过多上下文切换会拖垮负载。ResourceManager HA、双活再加Agent控制只是探索假设，不是成熟容灾方案。

## 5. 把决策和Bug复盘固化为可接手的工程资产

### 将每次决策和Bug复盘写进Docs与Skill，才有可接手的AI工程

从0到1后，生产化不只看可运行：单测、用例、用户动线、每个决策时间点、每个Bug复盘都要留。嘉宾要求AI出Bug后复盘，把方法沉为Skill；仓库留部署、架构、决策、重构、CI/CD、演进时间线、流程图、数据字典、为什么某节点抽象等文档。当前一个人OPC更需要这些，否则以后加入的同事不知道怎么改，甚至不知道该怎样用自然语言向AI提问。文档不是把AI聊天全存下来，而是能解释需求与改动原因的上下文。

让AI扫哪些重复模块可合并，仅提供候选；是否合并由业务理解决定。已有良好抽象后新需求是扩展，而非每次先堆屎山再大重构。压力约千并发时服务器有限，他会追问“是否还有更好方案、假设出现另一情形还成立吗”，不只是从模型给的ABCD选一个。

### 第二产品两天做到“半生产级”，后续见的是CEO

嘉宾把前套可实施路径用于第二产品，先覆盖幂等、组件降级、异步消息、全盘故障监控告警、熔断与切换等场景，再将容器配置、日志链路、灰度、数据备份、安全权限留为模板。他称两天串起流程与功能、全局高可用扩展设计，但主动限定只能算半自动化或半生产级，这与两天交付已验收的生产系统仍有距离。相比第一产品约一个月，是自述且任务范围未统一。前面说次日面试CTO，后文纠正为先见CEO汇报；最终并无CTO应聘成果的确认。

金融核心全球支付链路即便全测绿仍不能轻率上线，是他提出的风险边界；99.999和“三个九”混用且明确假设，不采用精确SLA。配置态或外围代码与核心运行交易代码需区别，不表示所有CRUD都无风险。Muse“已上线支付”只是别人评论触发他回应，不是产品官方事实。

### 前后端的竞争力不只在语法，而在可验证用户与系统结果

嘉宾不赞同“前端已死”：Node.js、JSX、React等是实现方式，价值还在产品审美、体感、流程串接与后端数据结构理解。例如页面从三秒变零点五秒是可衡量优化目标，文中并没展示这次已做到。懂业务如何在接口与用户动线间流转，比仅为学某技能而学更有迁移性。其认为工程基础有价值，与前人“剪辑岗位消失”预测是不同人的观点，不压成一致结论。

## 6. AICP旁路控制面：错误记忆、审计与token成本

### 终端命令失控的避坑重构：AICP 旁路控制面（堡垒机架构）
技术操盘手郭总在利用开源底座（如 DeepSeek 配合开源 Harness 编排框架）执行设备调试与后端轻量开发时，深刻体会到底层小模型在复杂系统交互中的脆弱性：
- **致命执行事故频发**：小模型在输出系统级命令时，极易因路径反斜杠漏写、Linux 提权参数拼错、目标服务器端口或库名混淆，造成意外删除、服务宕机或安全审计违规；
- **自研 AICP（AI Control Plane）控制面**：
  团队没有盲目去微调或重训底座模型，而是在大模型与受控服务器之间架构了一层**独立旁路控制面（AICP，类似运维堡垒机机制）**：
  1. **命令拦截与合规沙箱**：所有由 Agent 生成的 Shell 命令和数据库查询，必须经由 AICP 的语法树解析与危险指令黑名单（如 `rm -rf`、带通配符的表级操作）扫描，直接拦截越界高危动作；
  2. **错误记忆与自进化熔断（Error Memory）**：
     将每次真实运行中报错的上下文（输入指令、报错堆栈、失败原因）格式化写入 SQLite/向量数据库。当 Agent 下次生成相似指令时，控制面前置比对错误记忆库，一旦命中已知错误模式，强制拦截并在 Prompt 中即时注入反向避坑提示，形成无需重训模型的“经验自进化闭环”；
  3. **权限审计与全链路可回溯**：对每一步 Agent 调用的输入、输出、耗时和受影响资产做结构化存盘，满足企业生产网合规要求。

### 降本的核心抓手：三层漏斗与高频缓存拦截
讨论中对比了企业级 Agent 在面对多轮调用与多子 Agent 编排时的真实 Token 账单：
- **庞大 Prompt 膨胀的成本危机**：随着子 Agent 数量增多，每个任务都要携带巨幅系统设定、历史对话与工具定义，单次执行消耗数万 Token，算力账单急速上升；
- **博思 AI 的三层漏斗实战范式**：
  杨总分享了其在企业服务中沉淀的成熟降本漏斗：
  - **第一层（精确/分词检索拦截）**：针对企业常见的高频重复问题，直接通过本地分词库或精确键值比对匹配标准答案，命中直接返回，完全不调用大模型（0 算力成本）；
  - **第二层（向量相似度检索）**：未命中精确库时，通过轻量向量库检索经过验证的高质量问答对，相似度高于阈值直接复用历史结果；
  - **第三层（大模型兜底推理）**：只有前两层均未命中的未知长尾问题，才路由给后端大模型进行深度思考与推理；通过该三层漏斗，在保证服务质量的同时极大压低了 Token 消耗与推理延迟。

### 落地实操演练建议：终端 Agent 旁路控制面设计规范
1. **指令白名单与参数化模板强制约束**：
   - 严禁允许 Agent 裸执行任意拼接的字符串命令；必须将合法运维/业务动作固化为带参数的函数接口（如 `restart_service(service_name)`），由控制面做严格的枚举白名单校验；
2. **错误自检三步法（Error-Handling Loop）**：
   - 编写一段轻量拦截中间件：在命令发出前，检索当月历史错误库；若存在完全相同的命令模式且未做参数变更，直接向 Agent 返回“该模式在某月某日导致过某异常，请重新调整逻辑”，避免重复踩坑。

## 7. 陌生旧系统排障：沿输入输出补齐业务链

一位原七八人排班团队问老系统不稳、OOM、模块不熟怎么快速定位。杨总回应自己在浦发项目只剩需求人员时，先看报错cause by找类，再跟需求方确认该行之前做了什么、上游返回什么、每个方法对象输入输出什么，每次事故串好链。缺error日志时从现有info逐步往下加日志，第一次费劲但要留记录；即使猜接口猜中，次日复盘也要说明为什么，不能长期靠时间点捞个关键词猜。约一月把业务逻辑串通是本人历史经验。

业务稳定后如有大变更，可与产品/甲方讨论另起新系统，通过灰度引流、数据割接替换；这是建议，不是已经执行的迁移。提问者说现在截图交AI可语义关联定位，比以前快，嘉宾将深度思考比多人辩论。与“看模型思考”相比，可保留价值是证据和业务链的复盘。

## 8. 未上市IDE：先还原需求，再编程和人工发布

### 另一位二十多年开发者的IDE：自然语言与草图先还原需求

新来开发者说自己的IDE/Agent尚未完工未上市，正在最后外观包装，称三四个月前已申请专利但未核受理或授权，没有确认专利已获授权。他面向不懂技术的老板或业务经理：口语甚至方言先识别、拼出其认为约80%意思，再重构需求规格，自评审完善，有疑问问用户；业务逻辑→数据库设计→页面，也能文字加草图反推需求与库结构。需求说明、数据库、界面、功能细节、设计说明齐后评分过再自动编程，测试改Bug、打包，最后人工确认发布。普通用户可反馈看得见的外观，专业用户可提架构建议。他的目标是有半自动和全自动两套体系，质量、迭代与token成本才是难点。

### IDE差异定位与套壳商业：保密内网需求不等于所有推理已内网

开发者主张只做Java和C++、驱动、嵌入式、算法和跨硬件环境测试，认为与大厂通用语言Agent不同。一个人加AI的团队规模、专利时间、产品领先都是其自述，没独立测试。他愿付费定制功能、给客户品牌套壳，但不影响自己的独立上市；谈判价未给，不能当已售授权。有人问与WorkBuddy、Zcode、Codex、CC、DeepSeek Harness (DSH)等区别，他承认不少竞品没用，只用Claude Code和Cursor。

面向ToG/ToB有开发需求者，提出保密场景在内网使用；但被追问模型时又说可用开源模型，也可访问国内公网大模型。不能把本地Agent误写成底层推理数据不出网的保证。源码可深度定制、开源二开也可能有版权安全问题，均需核具体许可。未具名“DeepSeek DSH”与自称开源的另一开发者都是线索，尚无可确认的GitHub地址。

### 自研、二开、兴趣与商业机会，是四个不同问题

争论中有人认为Agent红海不如开源二开、该教育市场；开发者认为不同价位酒店仍有生存空间，主持人肯定个人兴趣开源或探索，不保证商业成功。二开钉钉的客户单、武汉想做比飞书更好IM、万人甚至十万人群是转述例子和目标，不是现成百万并发数据。关于OpenAI七百多数学成果没人研究是未证新闻，不作技术事实。能保留的判断方法是区分是否满足具体客户、自研必要性、许可与安全，以及是否有销售/交付能力，而不是“大厂有了任何小团队都不能做”或“只要敢做就会赢”。

## 9. 既有客户问数：接数据库只是第一步

### 大白的既有客户问数项目：困难不只是接一根AI接口

大白自述两月没上麦，走访约二十家旅游、地产、生产等中型企业，普遍AI尝鲜后低频，是其样本感受，不是总体统计。他认为编程、设计、视频短漫剧提效明显，提十二兆类似PS工具能做90%场景、朋友海外漫剧平台一天几部抽卡少，均未具名验证；品牌包装设计后的打样、生产仍在线下。WorkBuddy、豆包工作、千问工作、Codex、Claude是观察到的工具。

自己主要围绕过去进销存和供应链客户做AI统计分析，以前客户每要统计就加代码加公式，成本高。现尝试MySQL、SQL Server自有数据库，自建MCP接自建Agent，处理格式匹配、清洗；还有本地/云文件、第三方系统与电商接口，满意度仍不高。另一人也说做一年多集中清洗准确率，不能混成大白团队投入年限。正常字段匹配查询可做，复杂跨表、跨库、时效数据更难；未给经过验证的统一准确率。

### 问数的客户不是都能自己开发，要限定原有系统与实施范围

有原BI从业者主要接银行、保险、电信，认为此类客户已有IT团队，问数技术没多大门槛，项目本质常是现场外包或人力。大白回应自己做地方民营既有客户：过去已买其定制ERP/供应链软件，熟悉系统后再加AI升级，不主张一开始陌生客户就上整套AI。各地年销两三亿、十来亿企业缺IT能力、海南百家难有一家IT等是其走访自述。另一位坦承此前经验偏大金融通信，所说民营保险数据多系统分散还是十五年前案例，不能当今天现状。

### 聚水潭例子提示：不会用、不了解与主动不买，要分别验证

大白说见天猫、京东、拼多多多店仍各开浏览器人工统计，企业甚至不知道聚水潭类订单中台，ToB销售仍用Excel；买过的少数企业月末季末统一订单和业务统计很方便。另一人提醒统一账号可能触发平台关联处罚，但大白明确不熟悉不作结论。数字化工具可以买到不代表团队会操作；另有人正做FDE客户买SaaS仍靠Excel结合，未披露该项目具体成果。是否省钱、没听过、不会部署或担心账号，是不同原因。

## 10. MES说明书、源码图谱与RAG如何配合

### 工业存量系统之痛：文档遗失、千表复杂性与单纯 RAG 的死胡同
在传统重工业制造企业推行智能问数与 AI 助手时，技术团队普遍面临存量 MES/ERP 系统的致命泥潭：
- **十年老系统的文档断层**：经过多代外包与老员工更替，企业存量 MES 系统中上千个页面和业务表根本没有最新的说明书，连内部一线调度员都不清楚某些冷门统计报表背后的复杂计算公式；
- **单纯 RAG 的致命盲区**：如果仅仅把零碎的 PDF 操作手册塞进向量知识库做简单 RAG，大模型只能回答单页面的字面定义，根本无法理解“页面 A 输入工单 $\to$ 触发后台存储过程 B $\to$ 锁定物料批次表 C”这一深层数据调用链，导致在生成 SQL 或业务解释时频频产生致命幻觉。

### 源码逆向工程：从业务代码抽取 Markdown 手册与“源码知识图谱”
一位资深制造业数字化开发者分享了一套行之有效的破解架构：
1. **源码反向生成页面说明书**：
   编写脚本扫描 MES 系统的前端代码与控制器，提取每个路由页面的输入表单、查询参数、校验规则与业务流转说明，批量生成标准化的 Markdown 格式用户手册，系统性补齐企业知识短板；
2. **构建“页面—实体—存储过程—字段”源码知识图谱**：
   深入分析后端数据访问层（DAL）与数据库，抽取每张页面关联的物理数据表、外键依赖、调用的复杂存储过程以及最终允许对外呈现的字段，构建起系统级的源码知识图谱；
3. **两阶段精准路由与字段白名单防线**：
   - 当用户提出自然语言取数需求时，系统首先利用知识图谱将问题精准映射到对应的业务模块与功能页面；
   - 提取该页面严格绑定的**字段白名单（Field Whitelist）**，只允许大模型在该白名单限定的物理列名与关联关系内组装 SQL，坚决杜绝大模型在千表环境中无端外键拼接；
4. **安全隔离铁律：只读从库与写操作硬隔离**：
   智能问数底座必须严格接入企业的只读只分析数据库从库账号，严禁赋予任何生产主库的写权限；对于涉及修改生产排程或工单状态的操作，必须通过标准 API 走人工审批流，彻底杜绝数据污染隐患。

### 落地实操演练建议：传统工业系统源码图谱构建三步法
1. **扫描控制器逆向提取路由与参数字典**：
   - 编写 Python 脚本解析存量 Web 项目的 Controller/API 路由注解，提取出所有对外接口的输入参数、返回结构体与核心业务说明，导出为 JSON 规范清单；
2. **建立表级与字段级语义映射字典**：
   - 为高频涉及的核心生产表（如物料表、批次表、质检结果表）编写别名与业务口径对照表，将冷门英文缩写与一线业务行话做双向对齐；
3. **部署 Dify 工作流双轨分流**：
   - 在 Dify 等编排平台上构建问答分支：规则与制度咨询走非结构化文档知识库，数据查询走结构化图谱路由与参数化 SQL 模板，实现清晰的架构隔离。

## 11. 老板问数的需求与三层误差，要同时保留

### 问数三个风险与支持方回应，保留完整分歧

反对者指出老板问题漂移、需来回确认会不耐烦；语义层与LLM有幻觉；底层MES/WMS/ERP数据本就可能错，三层叠加后体验差，最终仍开会问现场。他说除了汽车行业几乎全不准是泛化判断，没有数据。支持方说自己已演示给中型客户，他们少开电脑、手机电话找财务或经理“帮查数”才是真需求；但复杂跨库跨表准确率仍低。

票券发行五十万张后查核销/未核销、区域门店和销售团队排名、指标、库存周转与调库是举例，不是本项目真实处理量或准确率。临时问数可帮助老板估资金和预备金，准确财务经营结论仍需部门会议；支持方也对软件真实价值和市场机会打问号。他又把图片视频软件市场说成大厂已全部占完、问数唯一机会，这是主观立场，与前述鼓励垂直自研的分歧并存。

### 自动汇报PPT随领导指标变化失效，是组织需求风险

一位曾在电动重卡企业的人说公司自动做汇报PPT的功能因一年后换领导、岗位指标变而全废；他明确从立项就反对，不是他接的订单。别人认为通用PPT大厂更强，应找企业差异化功能，但不能写成所有PPT定制都无价值。案例提示要区分现有报表持续使用和单一汇报偏好变化，不能因AI能做就把长期维护需求假设固定。

## 12. 农业投料和排程：先核现场闭环与数字化条件

### 农业数字化的使用能力，与饲料投料验证缺口是两人的经验

大白说自己另一团队做十年农产品电商，想给农业企业做商城、供应链数字化或物联网，却发现不少亲属式团队没有人会操作；其概括“不具备能力、资金和团队”不能推广全国。另一位自称双胞胎集团前自动化总监，用饲料投料反驳“大企业已经做到极限”：中控员对讲机通知现场投哪种料、哪投料口，现场口头报完，中控代报工，系统不能确认是否真正投料、重量或品类是否正确；投错影响库存、产品和客户投诉。他明确说这里只举需求例子，不知道怎么解决。

对方追问历史错误概率、老板重视程度，回应集团大小会都谈。真实问题存在，不等于有预算、有人愿改或能用AI解决；既不能把投料例子写成已部署视觉/称重系统，也不能因企业多年未数字化就判没机会。现场没有就此达成一致。

### 先问数字化为什么没做，再问AI能否落地

有人用“企业基因”解释数字化意愿，另有农业企业经历者提醒：有钱、有示范工厂不等于业务数据和流程真的通了，很多系统仅用于给领导展示报表。项目诊断应把预算、团队能力、业务目的、数据、模型和实际执行串起来，不能看到“灯塔工厂”就假设数据可直接供AI使用。“基因”只是讨论者的判断框架，不是不可改变的企业属性。

离散制造的排程例子尤其具体：计划要求先生产某件，但现场缺料，工程师便转做别的任务；排程系统如果接不到这种变化，计划就悬空。有人以自己的 Dassault APS 经历批评这类问题，这支持“核实现场约束与反馈”这一检查项，不能推广成所有APS无效，更不能推出每个问题都要AI解决。

## 13. 问数项目筛选、报价与真实交付毛刺

### 智能问数客户的筛选铁律：数据健康度比付费意愿更致命
一线走访食品、精密加工与连锁零售企业的技术顾问分享了残酷的获客现实：
- **付费意愿不等于交付可行性**：许多传统老板看到炫酷的“对话问数”演示后兴奋不已、极有付费意愿，但深入其机房才发现其底层数据是一团乱麻——只有老旧简陋的进销存，财务与收银系统各搞一套，历史订单全靠人工手账补录；
- **防范“一揽子包干陷阱”**：初创团队最容易犯的致命错误，是在合同中将“数据清洗、旧系统打通、数据治理与智能问数”混为一谈并给出一个固定的死价格。最终团队会被迫承担数月极其繁重恶心的数据泥潭清洗工作，导致整个项目深度亏损。因此，必须将“数据底座治理是否达标”作为售前立项的一票否决条件。

### 真实账本复盘：30 万元合同为何最终净利只剩 10%？
一位深耕制造与医疗问数交付的技术负责人，深度复盘了一笔刚完成验收的真实合同账本：
- **初期的美好预期**：合同金额 30 余万元，原计划 5 个月开发完成，扣除基础人力与服务器开销后，预计能保留约 50%（约 15 万元）的高额毛利；
- **拖延吞噬一切利润的深渊**：
  1. **数据私有化部署摩擦**：客户数据严禁出域，团队被迫派驻人员在客户机房封闭开发，差旅食宿与异地运维成本直线上升；
  2. **脏数据带来的语义黑洞**：大模型一连数据库就频频翻车，归根结底是历史数据中大量空值、乱码与非标缩写，团队不得不替客户倒贴 2 个月时间重做数据校验清洗；
  3. **无休止的新增报表需求**：客户各业务部门中途不断追加“顺便把这一类统计也加进来”的非标需求；
- **最终惨烈回报**：工期从 5 个月被迫拉长到 8 至 10 个月，团队人力被死死绑架，扣除全流程综合成本后，最终实际净利润仅剩 10% 至 15%（约 3–4 万元），扣除团队机会成本后在商业上基本等于完全失败。

### 落地自查清单：企业智能问数项目售前筛选四原则
1. **数据治理成熟度前置评估表**：
   - 进场前向客户发出《数据健康自评表》：核心指标是否拥有唯一计算口径？核心业务表是否存在系统性缺失？数据是否拥有规范的数据字典？低于 70 分的项目坚决不做一口价总包；
2. **两阶段分离签约机制**：
   - 严格将项目拆分为【一期：存量数据探查与指标治理（咨询与清洗收费）】与【二期：智能问数 Agent 搭建（技术部署收费）】两份独立合同；未通过一期数据验收，绝不盲目开启二期承诺。

## 14. 外包复制与ERP转包：差价之外的维护和责任

### 外包的隐性成本是后续产能被锁住

维护旧客户不是没有价值，但如果每次交付都需重建、大量驻场，人员会被旧单占住，无法接下一单。讨论提出两条方向：纵向聚焦一条行业产品线，以少量改动复制；或做足够小、交付边界清楚的AI任务。十家、百家、千家客户边际成本下降，是目标而非已经实现的规模效应。

“新增需求就加钱”只是一种建议，现场没有证明客户都会接受；软件项目外包与人员外包也有不同合同和责任结构，不能一句话判定都不可做。

### ERP转包的差价，不会自动消除主承包责任

有人设想二百万项目交给别人一百五十万，留下五十万；其他参与者提醒，合同可能禁止转包，客户追责仍找主承包商，承接方也可能退出。另一个实际ERP实施故事口述总盘“五百个”、实施分到八十多到一百多个，单位没有澄清，不能自动写成百万元。

三方链条是产品总部、客户与现场实施人员。现场报告问题，总部认为实施人员没理解，又让其重做，返工与沟通延迟把短工期拉长。这个故事支持提前写清问题判定权、产品缺陷与实施责任、客户变更流程，而不是证明转包一定有暴利。

## 15. 酒店评价表达工具：小需求、渠道承诺和竞品

大白从酒店运营朋友收到的需求，是让离店客人写飞猪、携程、同程评价时表达更完整。他口述两小时用 WorkBuddy 做了一个网页工具，朋友给了相当于“一个月加油钱”的红包，没有明确金额。对方说能帮推几十、上百套，是渠道承诺，不是已经卖出这些数量；小程序、App也未因此完成。

适用边界应是帮助真实客人表达真实经历，不能把它变成伪造消费评价。后续有人说用过有赞类似产品，9.9元起初不限量，三个月后改为100条；这是个人历史使用口述，不是当前官方价。发现竞品应回到自己的用户入口、实际操作便利与渠道，而不是仅因“已有工具”就否定需求。

## 16. 航运工作台：从纸面经验到关联业务数据库

### 航运重资产知识的结构化闭环：300天打磨20个岗位关联数据库
一位深耕国际远洋航运业数十年的高管，在离职后历时 300 多天，亲手用 AI 模拟并重构了近 20 个航运关键岗位（包括租船经纪、海务调度、机务工程、法务风控、航次财务等）的端到端工作流：
- **拒绝“孤立问答”假象**：通用大模型根本无法回答航运业的真实商业问题（例如“国际低硫燃油每吨上涨 50 美元，对我司当前船队有何影响？”）。因为答案不仅取决于油价，更取决于每艘船签署的具体租船合同条款（如长达 60 多页的 NYPE 纽约土产交易所期租合同标准范本中关于油耗补差的约定）、当前航线港口加油价格、装载吃水与经济航速等动态上下文；
- **构建全关联多维数据库**：
  管理者将航运领域海量的纸面规范、判例合同与船舶参数迁移至 Notion/知识库中，自建了跨领域与子领域的关联图谱（合同条款 $\leftrightarrow$ 法律风险 $\leftrightarrow$ 海事工程 SOP $\leftrightarrow$ 实时船位调度）。当一份真实合同上传后，Agent 能够自动提取所有核心权责并关联沿途港口气象与补给建议，彻底打破传统部门间的信息孤岛。

### 船舶安全配载的人机协同：AI 提方案、老船长把关签字
在极其严肃的船舶装载配载（Stowage Plan）环节，团队确立了严谨的人机分工边界：
- **多约束计算交由 Agent 初排**：将货品清单 Excel、集装箱重量分布、货舱尺寸结构、甲板局部受力强度限值等繁琐参数投喂给系统，由 Agent 快速生成多套符合船舶初稳性与剪切力平衡的初步配载建议；
- **安全底线始终由持证船长守住**：模型生成的方案绝非最终执行令，必须由资深持证老船长亲自复核审查、比对偏差并手动调校签字确认。这种人机协同将原本繁重的试算耗时缩减数倍，但在生死攸关的安全决策上坚决守住人类专业责任底线。

### 复杂业务极速新人赋能：大专英语小白接手专业海运流转
该系统展现出最具商业价值的人效突破：

### 落地演练抓手：重资产行业全关联知识库搭建三步法
1. **核心合同与标准范式结构化拆解**：
   - 选取行业最通用的长篇标准合同（如航运 NYPE、工程 FIDIC），拆解出关键权利义务与抗辩责任要点，录入向量库并打上规范的元数据标签；
2. **构建“资产—任务—规则”三维关联表**：
   - 在协同平台（Notion/Feishu/轻代码）中建立三张核心表：物理设备资产表（船舶/产线）、动态业务任务表（航次/工单）、外部环境参数表（油价/天气），设置双向外键关联，使提问天然携带多维上下文。

## 18. 企业AI落地的组织协作与FDE分工

### 企业AI落地需要授权与协作，不是单纯买模型

### 商务人员想要的，是需求与技术能力之间的翻译器

一位商务人员希望把Workbot等工具能做什么整理成能力目录，接到客户需求后可拆任务、判断可行性、成本和实施方式。现场认为这类工具可以做，但目录不能取代现场行业经验和特殊约束。

FDE究竟是岗位、部门还是一个OPC包办，有不同看法。成熟厂商的客户关系、品牌和长期服务形成信任，技术能力只是其中一部分。做过十年技术的人反思自己项目停滞，更倾向在既有系统里补一块确实需要的能力，而非每次重建全部系统。浪潮、软通智慧、华胜天成、腾讯企微、金蝶、用友是讨论里的厂商线索，不代表它们为任何特定交付背书。

## 24. OPC先验证订单，再承担经营风险

先有工作或小范围副业测试，找到少数真实愿意付钱的人，再考虑公司化；“十人中两人愿买”是举例，不是某产品转化数据。AI减少生产劳动，不会自动替代获客、注册、税务、收款和失败处理能力。家庭负债和最大可承受损失是约束，不能把背债等同能力差，也不能用成功故事鼓励无界加杠杆。

## 30. 珠宝销冠陪练与美业：采集、训练和交付复制

### 黄金珠宝水贝生态：智能工牌采录、销冠对练与知识库闭环
深耕深圳水贝与李朗黄金珠宝产业带的操盘手财神，分享了其团队在珠宝连锁门店落地“AI 销冠陪练”的完整业务链路：
- **线下门店的真实痛点**：传统金店员工流动率极高，老销售往往对核心话术秘而不宣，新入职员工培训成本高、开单周期长；
- **声卡/智能工牌数据采集链路**：
  为门店一线销售配备专业音频采集工牌，在日常真实接待顾客沟通过程中持续录音，经脱敏后回传至总部私有化系统。大模型从中提炼出成单率最高的话术模式、异议处理技巧（如克重金价计算、打折博弈、送礼寓意解答）以及 30 多个垂直子知识库；
- **模拟客户实战对练与过关考核**：
  Agent 根据提炼的知识库，模拟各种刁钻画像的进店顾客（挑剔型、比价型、预算有限型等）与新人销售进行实时语音多轮对练。系统对新人的倾听度、引导话术、产品知识准确性进行多维自动打分，只有对练考核达标才允许其实际上岗接客。

### 线下推行的隐性阻力：员工对抗心理与隐私利益博弈
与会行业专家深刻揭示了线下服务业推行 AI 工牌与对练系统时必须跨越的非技术暗坑：
1. **一线老员工的本能抵触**：
   在真实销售谈判中，销售员为了促成大单，常常会使用一些游走在边缘的私密承诺、人情让利或灵活话术。工牌全天候录音会让老销售产生严重的被监视感和不信任感，甚至引发故意遮挡工牌麦克风等软性对抗；
2. **美业/线下服务业的交付人力黑洞**：
   类似项目在向生活美容、美发等非标生活服务业推广时遭遇了严重的规模化瓶颈：美业店员数字化素养普遍偏低，仅仅把 SOP 包装成软件界面根本推不动，必须配备大量驻场服务人员手把手教学，高昂的人力实施成本会迅速吃空软件的毛利。

### 落地自查清单：线下服务业销冠对练系统的推行阻力防范准则
1. **利益分享机制前置设计**：
   - 严禁单向将智能工牌作为考勤与惩罚工具；必须建立激励机制（例如：贡献优质沟通案例被系统采纳录入知识库的员工，享受每月带单提成奖励或荣誉津贴），化被动抵触为主动参与；
2. **合规提示与隐私脱敏红线**：
   - 门店必须在显著位置向进店顾客提供《服务沟通录音声明》，音频处理必须在边缘端对顾客姓名、手机号、支付卡号等个人敏感隐私做实时脱敏。

## 41. 财务AI：从一个疲劳环节走向模块集成

### 财务AI分三层：采集治理、岗位自动化、辅助决策

财务询问者想企业自主逐步完善系统，不是要求全自动取代会计。技术建议先让发票等数据入系统，多系统CRM/ERP/MES做治理统一平台，查缺项和格式，再出成本/利润报表、告警和决策建议，未来预测更高阶。强调公司全局与个人成本会计、出纳需求不同；既有用友/金蝶/SAP导出的Excel等格式化数据可先做局部脚本，五张表汇总、Word转Excel、调整参数输出网页/报表。不要求初学者写Python，但需有运行环境，让AI调用包生成并保留通用脚本，需求变化再改。Python/JS包丰富程度是讲者个人经验，非绝对能力结论。

财务本人认可流程但追问非计算机人员怎么动手，另一非技术参与者指出技术回答没对齐甲方：个人小提效容易，商用/团队系统还要理解GitHub、数据库、服务器与本地环境。别从完整系统起步，先选一个疲劳环节、定义目标、搭环境、验结果迭代。原讲者称跑通过网站操作、文档转表、固定周月报；没展示生产财税验收。

### 浏览器填报与安全隔离：人保留采集、检查和提交责任

财务询问税务网站自动申报，建议浏览器操作Skill从Excel填表，原名Playway/Play with不清，工具身份待确认。按正常人节奏登录、不高频刷；安装本地可调用环境的客户端，网页聊天不一定能触达本机。把流程跑对后固化模板/脚本，定期运行，用户保留数据采集及输出查看。没有展示税站验证码、授权、申报校验全覆盖，不编成全自动报税SOP。

关键安全做法：专用目录放文件副本，限制AI操作范围，初期用权限受限模式，要求不自行危险操作；改完检查后再复制回，原文件不直接改。目录隔离减风险而不是保证绝对不会损害系统。有人用chatbook近音的免费客户端、自配Skills，API另付费可换DeepSeek/GLM；Workbot等名称近音及只能用自家云的说法待核。Codex建议：先让它执行实际步骤→人工指出不合格处→改到合格→要求把成功流程做成Skill，下次调用。固化成功路径而非第一次输出。

### 财务多角色协作：模块化低耦合，个人脚本和FDE集成是两种规模

成本、销售、出纳按树形结构分模块、再分机器成本；处理一次后固化脚本，换电脑改路径仍可复用。低耦合让A运行少影响B，但数据准确、业务逻辑和接口约定仍是前提。有人建议多Skill聚成Agent、严格提示词使输出稳定，这属于方案主张，不是稳定性实测。财务追问不同人做的模块怎么组合，回应若要求成熟跨角色系统可找FDE，不要自己拖很久。

FDE建议用授权数据库/API直接接用友、金蝶、SAP，减少窗口导入导出；统一数据中心/API消除孤岛，权限拿不到就不能拿数据。个人办公脚本与企业集成的成本、职责不同。附近企业5000–10000招FDE、小企不愿花钱均个人观察，不是薪资市场结论。

## 43. 模型排错与可迁移工作流：用真实任务并测

一人Codex生图改一天，最后称是协议/HTML传输方式问题，换两条网络也没好，具体协议未披露，不能杜撰修复参数。国产API接好后稳定、进口会员便宜等是互相不同使用经验，未经同任务对比；GLM新高速、5.3、500字/秒、GPT百万token几毛都是口述待核，非技术规格。会员模拟API等不整理为绕限制教程。

可执行方法是API调用设计通用配置，换URL与配置切换厂商；脚本/模板开发时拿**三家模型同任务并测**，避免只贴合单一API，一换厂商性能崩溃。按业务选择模型，而非一个模型包打天下；有的业务一个好、另一个不好就换。百分之70可用、95%成功率及可进化模型每月更新、AGI几十年等是个人估计，不作为基准或事实。明确目标和可判对错的验收条件，比无标准的生成更易检验。彩票随机数/概率说法未给可靠证明，不传播成提高中奖方法，保留时间投入应与真实结果比较的提醒即可。

## 44. 铁路检测与交通预测：具体痛点，不等于已有成熟方案

### 接触网照片的海量人工比对

一位铁路检测企业管理者说，公司2019年已用卷积神经网络做视觉检测。他举高铁接触网悬挂为例：检测车经过时，每根支撑柱正面约25张、背面约25张，合计约50张；柱间距约30–50米，100公里便产生海量照片。他说现场仍大量依赖人眼比对，缺少能非常准确定位缺陷的AI。

另一个机会是随列车振动产生物理形变的装置：已有监测数据，可探索从历次变化预测后续趋势；这属于他提出的方向，没有给出已验收的预测系统。隧道顶部空鼓的例子同样区分现状与建议：他口述现场会在列车经过前人工检查处理，建议结合超声波或热探测与AI分析，但未提供具体设备、实施参数或安全验证。

### 数据孤岛部分打通后，预测仍可能做不成

他还讲到2023年承接武汉交通管理部门项目：预付款口述“三百”，单位未明确。客户部分打通数据孤岛，希望预测网约车等运营车辆未来交通拥堵，以便调度。其团队做了约一年半仍没有完成目标；上海浦东同期另一团队也做不到的说法是他的转述，没有独立项目材料。这个案例说明，数据能接入只是前提，不能因此承诺复杂时空预测一定成功，更不能把预付款当项目验收或利润。

### 专业小团队与三五人团队，准入条件仍未讲清

他举上海“儒/如慧”近音公司专做接触网检测，人数口述约二十至四十人，名称与规模待确认；认为企业小不代表无法接专业大客户订单。主持人进一步追问一两人、三五人团队如何从投标角度进入，发言中断，没有得到完整答案。

这位管理者也认为统计、生成式管理需求有限，问CFO或CTO即可获得进展，报表还可能鼓励把数据做漂亮。这是其管理立场，与民营企业问数客户的需求并不一致；两者服务的组织、权限与问题不同，不应以一方经验否定另一方。
